# 审计验证框架

这份文档讲**怎么验**：拿到一条事件流或一个信任包之后，用什么命令、看哪些结论、哪些失败意味着什么。
格式规定见 `docs/event-log-spec.md`，完整步骤见 `docs/deploy-and-demo.md`。

## 1. 先选对工具

| 你手上有什么 | 用哪个 | 命令 |
| --- | --- | --- |
| 一份 `events.jsonl` | `tools/verify-stream.mjs` | `node tools/verify-stream.mjs <事件流>` |
| 一个信任包目录（含 `trust-bundle.json`） | `tools/verify.mjs` | `node tools/verify.mjs --dir <包目录>` |

两者都是**零依赖**的：只用 Node 内置模块，不需要联网，不需要安装本产品。
拿信任包去喂 `verify-stream.mjs`，或拿裸事件流去喂 `verify.mjs`，都会得到明确报错而不是含糊的「通过」。

退出码统一：**0 = 通过**（可能有警告）、**2 = 存在完整性问题**、**1 = 用法或读取错误**。
接流水线时看 0 与非 0 即可；要细看就加 `--json`。

## 2. 信任包校验：六个检查，逐个过

`verify.mjs` 按顺序做六件事。前一件不通过，后面的结论就没有意义 —— 这也是它按这个顺序排的原因。

| # | 检查 | 通过时的代码 | 它回答的问题 |
| --- | --- | --- | --- |
| 1 | 包内校验和 | `PACKAGE_SUMS` | `SHA256SUMS.txt` 列出的每个文件都与记录一致吗 |
| 2 | 清单指纹 | `BUNDLE_DIGEST` | 这份清单是不是**你收到的那一份**（需要外部提供指纹） |
| 3 | 清单签名 | `BUNDLE_SIGNATURE` | 清单由哪把密钥签署、签名是否有效 |
| 4 | 检查点签名 | `CHECKPOINT_SIGNATURES` | 每个已签名检查点是否验通（离线完成，不依赖事件流） |
| 5 | 可信时间戳 | `TRUSTED_TIMESTAMPS` | 每个时间戳令牌是否验通、最早签发时间是什么 |
| 6 | 事件流哈希链 | `EVENT_CHAIN` | 链是否完整、是否与清单声明的链头一致、创世锚点是否匹配 |

第 2 步是唯一**无法由包自己完成**的一步：包可以自证一致，但证明不了「它就是你收到的那一份」。
没有外部指纹时，它会给出警告 `BUNDLE_DIGEST_UNPINNED`，而不是假装通过。

## 3. 带着外部固定值验（唯一不能省的一步）

```bash
node tools/verify.mjs --dir ./bundle \
  --expect-bundle-digest <64 位十六进制> \
  --expect-signing-key ed25519:<16 位十六进制> \
  --expect-tsa <TSA 证书指纹>
```

- `--expect-bundle-digest`：清单指纹。**必须走另一条渠道拿到**（当面、电话、纸质件）。
  这是整条链上唯一无法由包自己证明的环节 —— 也正因为如此，改包的人无法同时改掉你手里那串值。
- `--expect-signing-key`：固定签名公钥。不固定的话，验的是「包内嵌入的公钥能验通包内的签名」，
  那只能证明包是自洽的，不能证明它出自谁。
- `--expect-tsa`：固定时间戳机构的证书指纹，防止把令牌换成一个自签的。

三个都给上，才做到「**连包带清单一起换掉也能发现**」。只给其中一个，防的是其中一类替换。

## 4. 结果怎么读

每一行形如 `✓/!/✖ [CODE] 说明`：

- `✓` 通过；
- `!` 警告 —— **不阻塞通过**，但需要你判断。最常见的是「未提供外部指纹」。
- `✖` 完整性问题 —— 结论是不通过，退出码 2。

末尾一行给结论：`结论：通过（N 项警告需要留意）` 或 `结论：不通过（N 项完整性问题）`。

`--json` 输出结构化结果，含 `ok` / `failed` / `warned` / `checks[]`，便于接进 CI。

## 5. 事件流校验：改动会被指到第几条

```bash
node tools/verify-stream.mjs examples/demo-event-stream.jsonl
node tools/verify-stream.mjs examples/demo-event-stream.jsonl --pubkey ed25519:0123456789abcdef
```

输出里会明确给出链式事件条数、检查点数与验签通过数，出问题时给到**条号与事件类型**：

```text
结论：存在 1 个完整性问题
  ✖ [AUDIT_CHAIN_HASH_MISMATCH] 事件内容哈希不匹配（第 6 条，type=tool.action_completed）
```

不带 `--pubkey` 时，它用事件流里嵌入的公钥验签，并明确提示这一点（`提示：使用事件流内嵌公钥校验`）——
那能发现内容被改，发现不了「连密钥带内容一起重写」。

## 6. 信任包里有什么

```text
<信任包目录>/
  trust-bundle.json       清单：密钥、检查点、范围、上限、摘要
  verify.mjs              零依赖校验脚本（就是本仓库 tools/verify.mjs 的那份逻辑）
  SHA256SUMS.txt          包内全部文件的哈希（含签名文件自身）
  README.md               给接收方的说明与命令
  checkpoints/*.tsr       可信时间戳令牌（如有）
  audit/…                 事件流副本（脱敏版与原始版，取决于打包时的选择）
```

接收方需要的东西只有两样：这个目录，以及从**另一条渠道**拿到的清单指纹（与公钥，如果要做来源固定）。

## 7. 这套框架不承诺什么

- **不验证内容是否真实**。它证明的是「这份记录自写入以来没有被改动」，不是「记录里写的事情真的发生过」。
  一条从一开始就写错的记录，链是完整的。
- **不证明签署者是谁**。除非你把公钥带外固定，否则它只说明「由某把密钥签署」。
- **不阻止整体重建**。拿到工作区读写权限的人可以连私钥一起换掉，重新造一条自洽的流。
  要防这个，只能靠带外公钥固定，或把私钥移到工作区之外。
- **不保证时间**。时间戳证明的是「在 TSA 签发的那个时刻已经存在」，不证明事件发生在那一刻之前多久。

把这四条写在最前面，是因为一个声称做得比实际多一点的验证工具，比一个诚实的要危险得多：
使用者会把「验过了」当成结论，然后据此签字。
